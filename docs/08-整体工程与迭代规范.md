# 整体工程与迭代规范

这个项目的最终形态是一个持续演进、始终可运行的 Arduino 固件工程，不是一组做完就丢的阶段练习。

## 代码归属

正式代码由你亲手实现。我的职责是：

- 设计模块边界和接口
- 提供可供参照的实现代码
- 检查你的代码和硬件接线
- 定位编译错误、协议问题和运行问题
- 维护项目文档和目录结构

默认不写入或修改 `.ino`、`.h`、`.cpp` 等代码文件。只有你明确说“写入工程”“计入”或“按这个修改文件”时，我才会落盘。

## 固定服务端边界

本工程始终连接小智服务，不实现或替换为以下方案：

- 设备端自建 ASR、LLM、TTS 链路
- 直接使用豆包、Coze 或其他第三方服务密钥
- 把某个 WebSocket 地址永久写死在业务代码里

固定流程是：

1. 连接 WiFi
2. 请求小智 OTA
3. 保存并解析返回的 WebSocket 配置
4. 按小智协议完成握手、音频发送和接收

M3 之后增加的网络代码必须遵守这条边界。协议参考以 `78/xiaozhi-esp32` 和 [05-联网与协议.md](05-联网与协议.md) 为准。

## 唯一工程入口

所有正式代码都在：

```text
firmware/xiaozhi/
├── xiaozhi.ino
├── data/
└── src/
    ├── app/
    ├── audio/
    ├── core/
    ├── hal/
    ├── net/
    └── ui/
```

在 Arduino IDE 中打开 `firmware/xiaozhi/xiaozhi.ino`。文件夹名必须和主文件名一致。

`src/` 下的源码会由 Arduino IDE 递归编译。模块按职责放入 `core`、`hal`、`audio`、`net`、`ui`、`app`。

不要为 M1、M2、M3 分别建立长期项目。里程碑是交付顺序，不是多套产品。

工程在每个里程碑结束后都要保持可编译、可上传、可观察。

| 里程碑 | 对同一个工程增加什么 | 保留什么能力 |
|---|---|---|
| M0 | 工程、配置和启动入口 | 工程能编译上传 |
| M1 | 按键、状态灯和 LCD | 状态可见，长按不连发 |
| M2 | 麦克风、功放和音频链路 | 本地音频能采集、播放和回环 |
| M3 | WiFi、OTA 和 WebSocket | 能拿到会话并重复重连 |
| M4 | Opus 解码和下行播放 | 能播放服务端语音 |
| M5 | Opus 编码、上行和状态机 | 能完成完整对话 |

## 模块如何加入

每个能力优先做成一对文件：

```text
src/hal/Button.h / Button.cpp
src/hal/RgbLed.h / RgbLed.cpp
src/ui/Display.h / Display.cpp
src/audio/Microphone.h / Microphone.cpp
src/audio/Speaker.h / Speaker.cpp
src/audio/AudioPipeline.h / AudioPipeline.cpp
src/net/Network.h / Network.cpp
src/net/Protocol.h / Protocol.cpp
src/app/Application.h / Application.cpp
```

`xiaozhi.ino` 只负责：

1. 初始化串口和基础硬件
2. 创建各模块对象
3. 调用各模块的 `begin()`
4. 在主循环或任务里驱动模块

具体实现留在对应 `.cpp` 里，引脚和常量集中在 `src/core/Config.h`。

## 什么时候允许单独做实验

单独实验只用于验证一个不明确的硬件或库，不是最终项目的一部分。

例如：

- 确认一个未知型号的 LCD 能否点亮
- 确认麦克风接线正确
- 确认功放能响
- 验证某库是否能在 Arduino IDE 编译

实验通过后，把已经验证的最小代码合并回 `firmware/xiaozhi/`，然后删除或归档临时实验。不要维护多份长期并行的代码。

## 迭代方式

每次只做一个小步：

1. 写下一个可以验证的目标
2. 增加一个模块或一段最小功能
3. 编译并上传同一个 `xiaozhi.ino`
4. 查看串口、灯或屏幕的反馈
5. 记录版本和验收结果
6. 通过后再开始下一步

建议每完成一个里程碑，就在 `src/core/Version.h` 中提升版本号，并写一段交付记录。

## 出错时怎么回退

如果新功能破坏了已有能力：

1. 先恢复上一个可运行版本
2. 再用最小实验定位新问题
3. 修好后继续集成

正式工程的每个可运行版本都应该是整体工程，而不是一个脱离上下文的示例片段。
